# Release notes are authored per-PR as fragments, not drafted from commit history at release time

An earlier design had the release pipeline call Gemini to draft English release notes from the commit log, pause on a GitHub-environment approval gate for the maintainer to edit them, then call Gemini again to translate into other languages — all at release time. We rejected this in favor of small **note fragment** files (`.release-notes/<slug>.yml`) added per-PR while the change is fresh, written directly by whoever implements the change (typically a Claude Code skill, invoked automatically when finishing a branch). Translations, where included, are written by the same author at the same time — no AI/LLM call happens anywhere in the release pipeline itself, and there is no approval-gate pause, since fragment content already goes through ordinary PR review. A purely mechanical script concatenates whatever fragments exist into that version's entry at release time.

We picked this because reconstructing user-facing intent from commit messages after the fact is strictly harder than writing it down while you still remember why the change matters, and it removed an entire category of release-time failure modes (API quota/latency, an approval step nobody remembers to complete, drafts that misread commit intent). The trade-off is that release notes now depend on PR authors (or their tooling) remembering to add a fragment — mitigated by a CI check that fails PRs touching `src/`/`electron/` unless they add a fragment or carry a `no-release-notes` label.
